# Agent guide

CLI and MCP server for the TF Hub API, built on the unjs ecosystem (citty, consola, ofetch). The
published bundle runs on plain Node; Bun is the development runtime and powers the compiled binaries.
Small, typed, consistent — the CI gate enforces all of it.

## Commands

```sh
bun install
bun run dev -- whoami   # run locally with args
bun test                # bun:test suite (tests/, preload isolates the config directory)
bun run typecheck       # tsc --noEmit (src, tests, scripts, configs)
bun run lint            # oxlint, deny-warnings
bun run fmt             # oxfmt
bun run knip            # unused exports, files and dependencies
bun run build           # node-ready bundle to dist/index.mjs (CI enforces a size budget); the
                        # `--conditions=worker` flag makes ofetch resolve to its universal entry —
                        # Node >= 22 has native fetch, so bundling node-fetch-native would be dead weight
bun run build:binary    # standalone executable for the current platform (dist/tf-hub)
bun run generate        # refresh the OpenAPI spec and regenerate Zod schemas
```

Run `lint`, `fmt:check`, `knip`, `typecheck`, and `test` before handing work over — CI runs all of them
plus typos, zizmor (workflow audit), Codecov and the bundle-size check.

## Architecture (vertical slices)

One folder per feature domain; everything wires up exactly once.

- `domains/<domain>/` — `api.ts` holds endpoint paths (`api/paths.ts` helpers), typed calls that parse
  responses with the **generated** Zod schemas, and response-shaping helpers (e.g. `omitBio`); small
  single-resource domains may inline their calls in `index.ts` instead. `index.ts` holds
  `defineDomain({ name, description, actions })`.
  Each `defineAction` pairs a Zod input schema (the single source of CLI help and MCP tool docs via
  `.describe()`/`.default()`) with `run` and `render`. From that one definition the registry derives the MCP
  tool `<domain>-<action>` (with verb-derived annotations) and the CLI command `tf-hub <domain> <action>`.
  Single top-level commands use `standaloneEntry`. Register new domains in `domains/index.ts`.
  CLI and MCP both execute through `runOperation` (`domains/operation.ts`), which turns truncated pages
  into notices and adds the `mine=true` hint to a 403 on operations that can read your own records.
- `api/` — `client.ts` (ofetch transport: auth header, `{ data }` envelope unwrap, `ApiRequestError` with
  the HTTP status and server message), `paging.ts` (records lists whose `metadata.totalItems` exceeds what
  was returned), `paths.ts`, and `generated/zod.gen.ts` — regenerated by `bun run generate` from the live
  OpenAPI spec (`openapi.json` is gitignored; `scripts/openapi-normalization.ts` documents why responses are
  made tolerant and which noise fields are dropped). Never edit generated files; the generated folder is
  excluded from lint/format/knip.
- `cli/` — output helpers (`tableRenderer`/`detailsRenderer`/`deletedRenderer`, `formatValue` for the `—`
  placeholder, `printJson` — indented in a terminal, compact when piped), the Zod→citty bridge, `usage.ts`
  (command lists show headline summaries, a command's own `--help` appends the full description), error
  handling and paging notices on stderr, update notifier. The notifier and the `update`
  command detect standalone binaries (`runsAsStandaloneBinary`) and point those users to the GitHub
  release assets instead of a package manager; `scripts/build-release-artifacts.ts` cross-compiles
  the linux/darwin/windows binaries that the release workflow attaches to every GitHub release.
- `mcp/server.ts` — registers every operation as an MCP tool over stdio and returns compact JSON, preceded by
  one text block per paging notice (first, so a client that truncates long results still sees it). The server instructions carry the cross-tool conventions (identity,
  `mine`, paging, formats, update semantics). Stdout carries JSON-RPC; logs go through `mcpConsola`
  (stderr). The SDK parses tool arguments — never re-parse them.
- `commands/` — interactive-only commands (`login`, `logout`, `mcp-server`, `update`).
- `auth/` — Firebase browser login (h3), token refresh, and credential storage in an owner-only
  file (0600, XDG config path) — the npm/gcloud/docker model, chosen over the OS keychain to avoid
  keychain confirmation prompts on every invocation.
- `config.ts` / `runtime.ts` — all constants; runtime holds base64-obfuscated **public** identifiers only.

## Add an operation

1. In `domains/<domain>/api.ts`: endpoint path + call function parsing with the generated `zXxxDto` schema
   (run `bun run generate` first if the DTO is new on the server).
2. In `domains/<domain>/index.ts`: a `defineAction` with a described input schema (reuse `domains/fields.ts`
   helpers — `limitField`, `monthField`, `uuidField`, `explicitBooleanField` for booleans in updates,
   `commaSeparated*Field` for lists, `jsonField` for nested payloads; they accept both the native JSON type
   MCP clients send and the string a CLI flag carries), a `run`, and a `render`. Override `annotations` only
   when the verb misleads (e.g. a POST that changes nothing).
3. New domain? Create the folder and add the entry to `domains/index.ts` (order = help order).
4. Add a focused test in `tests/` — assert behavior and failure paths, never trivia.

## Data, not answers

The CLI and the MCP tools are a data faucet, never a calculator. Agents and shell pipes do the math —
`game show --json` plus one `max()` answers "who has the most XP" with zero new code, and that is the
desired state, not a gap. Before adding anything, apply this test: _can an agent answer the question from
one existing call's `--json` output with a trivial transform?_

- Yes → no code. Resist the convenience method.
- No, because the data is distorted (wrong units, embedded base64, HTML noise, N+1 calls, selectors nobody
  has at hand) → fix the data fidelity here. This set is finite and every fix helps every future question.
- No, because the server does not expose the data → server backlog, never client-side computation.

Two narrow exceptions: presentation sugar in `render` (totals under a table, sorting) — humans cannot pipe,
and agents never see renders; and generic mechanisms that amortize across every operation (`--mine`
resolution, help summaries, `plainText`, paging notices) — one implementation for all, never a method for
one question.

Agents pay for every token of a result, so fidelity includes size. Rich text leaves `run` as plain text;
bulky fields are opt-in (`withBios`, `withContent`); data a record repeats from elsewhere is dropped (the
directory's position permissions live in `positions-list`); and fields no consumer reads (avatar URLs, self
links) are removed from the response schemas during normalization.

## Code requirements (non-negotiable)

- English everywhere, correct grammar; no abbreviations in identifiers, files or folders.
- No comments — except the rare one that protects a non-obvious decision from being "fixed" later
  (server quirks, spec normalization rationale, security context). Everything else must be readable
  without documentation; prefer renaming and extracting over commenting.
- Early returns, no `else` after `return`, blank lines between logical steps inside functions.
- Template literals over string concatenation (wrapping long literals across lines with `+` is the
  one allowed use); the newest stable JS/TS syntax that improves clarity
  (labeled tuples, `Promise.withResolvers`, `toSorted`, …).
- `src/` must stay Node-compatible: `node:*` and web APIs only, no Bun globals (the lone guarded
  exception is the compiled-binary check in the update notifier). Bun APIs are fine in `scripts/`
  and `tests/`. Prefer unjs/maintained libraries over custom code — but never add a dependency to
  replace fewer than ~10 lines.
- One logger: consola. MCP mode logs via `mcpConsola` only (stdout must stay clean).
- Validate untrusted JSON with Zod at the boundary; never cast with `as`.
- Repeated literals become shared constants/helpers (`formatValue`, field helpers, …).
- CLI help and MCP descriptions: complete enough to use the operation cold, no longer than that.
- The company behind this project is never named anywhere in the repository — refer to it generically.
- No secrets in the repo, ever. Errors must stay secret-free.
- [Conventional Commits](https://www.conventionalcommits.org) drive the changelog (changelogen).
